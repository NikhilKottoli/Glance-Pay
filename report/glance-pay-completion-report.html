The product

One sentence. One payment.

RupeeRail needs a UPI QR string. Glasses have no camera. Glance Pay is the bridge: location + voice → merchant QR payload → existing quote / sign / pay flow.

Hardware truth

Text lens, mic, touch/ring input. No camera. No speaker. Apps run on the paired phone.

Safety truth

Dedicated low-balance session wallet, capped vault allowance, daily limit, explicit confirm.

Reuse truth

No new protocol. RupeeRail contracts and payout rail stay untouched.

CHECKPOINT 4

Phase 4 — Voice to amount

“Pay 12.50” becomes a validated amount plus an optional merchant hint. A pure parser; no side effects.

Accepted phrasing → parsed result

"pay 12.50" → { amount: 12.50 }

"pay twelve fifty" → { amount: 12.50 }

"pay 200 to Blue Tokai" → { amount: 200, merchantHint: "Blue Tokai" }

"pay 50 rupees" → { amount: 50, currency: "INR" }

Rejected

No amount · negative · zero · absurdly large · ambiguous phrasing.

Work items

  • Get audio or transcription from G2 to phone using the Phase 1 finding; document the STT choice and tradeoffs.
  • Pure, well-tested parser: text → { amount, currency?, merchantHint? }.
  • Echo parsed amount on the lens before moving on — catch mishearing early.
  • Configurable per-payment cap at parse time, default ₹500 for the demo.

Acceptance

✔ Tests pass, incl. Indian-English numbers & decimal edges
✔ Spoken amount appears on lens
✔ Over-limit/invalid refused with clear lens message

glance-pay / report08 / 14Phase 4
CHECKPOINT 5

Phase 5 — Merchant resolution

The core novelty: location + voice hint → a merchant with a real UPI QR payload.

Registry

  • data/merchants.json, validated loader.
  • Fields: id, name, address, lat, lng, upiUri, category, aliases[].
  • 5–10 seeded entries, including a close pair ≤ 30 m apart and one real test merchant for the live demo.
  • Validate upiUri format at load time.

Ranking & disambiguation

  • Distance weighted by reported GPS accuracy; fuzzy name match; alias match; optional recency.
  • Return top 3 with scores.
  • Strong single match → still CONFIRM. Never auto-pay.
  • Otherwise → PICK_MERCHANT. Nothing in range → “No merchant nearby”, exit.

Integrity & privacy

  • Confirm screen shows registry name and shortened UPI handle to expose wrong/spoofed entries.
  • Handle permission denied, low accuracy, stale GPS fixes.
  • Location and payment history stay on-device; no analytics, no raw-location upload.
  • Wi-Fi/BLE ranking = stretch; otherwise future work.

Acceptance

✔ Unit tests: close-pair disambiguation · name-hint override · no-match · poor-GPS accuracy   ✔ Scripted fake-GPS simulation yields correct candidates   ✔ Sensible pick list on device/simulator

CHECKPOINT 6

Phase 6 — Real payments & safety

Confirm on the lens → a real testnet payment through RupeeRail, with safeguards that never leave the user unsure whether money moved.

Payment path

  • PaymentService interface (quote → sign → submit → poll); mock and real implementations swappable.
  • Dedicated low-balance session wallet; best available secure storage; capped vault allowance verified on-chain; remaining budget on debug screen.
  • Quote must be fresh at confirm; expiry → re-quote + re-confirm, never sign stale silently.
  • Confirmation single-use and tied to one {merchant, amount, quote} — double tap cannot double-submit.
  • Extra friction above a threshold; client-side daily limit in addition to RupeeRail’s.

Status, failures, audit

Paying…
Paid ₹12.50 to Café X
Failed, refunded · Pending, check phone
  • Dispute window exposed on phone; “dispute last payment” reuses the existing flow.
  • Network loss, backend down, quote rejected, payout failed → clear lens message + safe terminal state.
  • Local audit log: timestamp, merchant id, amount, state, tx hash — no secrets.

Phase 1 research gate

Open questions & risks

The plan deliberately refuses to invent APIs. These are answered from real docs/code and recorded in CHECKPOINT-1.md before any feature work.

Questions to answer

  • Which G2 SDK/runtime and language? Is there a simulator?
  • Raw mic audio, SDK transcription, or neither? (Shapes Phase 4.)
  • Mock payout rail in services/api-py, or must we stub one?
  • Which chain do we demo on, and where are the faucets?
  • Where can the session key be stored securely on the phone runtime?
  • Do the vault’s per-payment/daily caps constrain demo amounts?

Risk register

● G2 SDK names unverified — research from official docs; if unresolvable, stop and ask.

● Payout credentials — the demo must not need real Razorpay keys; find the sandbox/mock path.

● GPS accuracy — close merchants need accuracy-aware ranking; no guessing.

● Mitigation — mock mode from Phase 3 makes the whole UX demoable with no network or hardware.

Rule: if blocked after a short attempt, stop and ask — never silently work around a safety item.
